EF Core and Dapper in one unit of work

EF owns writes; Dapper owns grids and reports. Both share one connection and one ambient transaction, so a report sees flushed-but-uncommitted rows and can't deadlock against the write that produced them. The unit of work is replayable to cooperate with EnableRetryOnFailure.

⛨

Per-user isolation in four layers

A global query filter that EF parameterises per execution, no context pooling, a write-side ownership interceptor, and owner_id = @UserId on every Dapper query. Cross-user access returns 404, not 403.

⚿

The browser never holds a token

A 15-minute JWT and rotating refresh tokens (256-bit, SHA-256 hashed, grouped into families) live inside an encrypted HttpOnly cookie. Replaying a used token revokes the whole family.

⌗

Injection-proof grid queries

Kendo field names map through a per-grid allow-list to fixed SQL expressions, operators come from a closed set and values are always parameters. Paging is bounded and every sort gets a stable tiebreaker.

⚑

Security hardening

No secrets in the repo, per-IP rate limiting on auth endpoints, CSP and security headers, antiforgery on every POST, and a database and API that publish only to loopback.

▶

Push to deploy

GitHub Actions builds with warnings as errors and checks formatting, then pushes SHA-tagged images to Docker Hub and deploys over SSH with a pinned host key using docker compose up --wait.

Design decisions, with reasons

UUIDv7 primary keys
Time-ordered, so they keep the InnoDB index locality that random GUIDs destroy.
EF Core 9 on .NET 10
Pomelo has no EF Core 10 build, and mixing major versions breaks the provider ABI at runtime.
Source-generated Mediator
MIT licensed, with no reflection or assembly scanning. MediatR moved to a commercial licence.
Soft delete only on transactions
MariaDB has no filtered indexes, so unique constraints can't be scoped to live rows.
